1. ORDER OF WORK
================
  1. READY  Build the bundle:  pwsh scripts\build-android.ps1 -Variant play -Clean   (needs the upload key in %USERPROFILE%\.plax-signing).
  2. READY  Check it:  node scripts\check-bundle.mjs   (it must end with "all checks passed"; it writes artifacts\aab-verification.json).
  3. OWNER  Upload artifacts\plax-2.0.0-play.aab to the production track (or to testing first). The package is com.plaxlabs.news, the same
            as the native app, signed by the same upload key, with version code 20 (the native 1.7.1 was 18): Play accepts it as the next
            version of the same app, and every install is updated in place (section 9).
  4. OWNER  When the Console shows the advertising ID message, choose "Release without permission" (section 2).
  5. OWNER  Section 5 (one line in Data safety), section 6 (release notes), section 8 (the publisher's name).
  6. OWNER  After the release is live: look at "App bundle explorer" for the version codes that are still active, and at the pre-launch report.
            The size the Console shows for a phone is the download size, about 14 MB, not the file's 55 MB (section 12).


2. THE ADVERTISING ID MESSAGE ("Release without permission")
============================================================
What it says: "Your advertising ID declaration says that your app uses advertising ID. A manifest file in one of your active artifacts doesn't
include the com.google.android.gms.permission.AD_ID permission", with two buttons, "Update declaration" and "Release without permission".
Why it appears: Play checks every active artifact of every track, not only the one being uploaded. The 2.0.0 bundle has the permission (the Google
Mobile Ads library adds it, and check-bundle.mjs fails if it is missing). An older artifact that is still active on some track does not: the
ad-free 1.5.x builds, which never held it. It is a warning about that old artifact, not a fault in the new bundle.
What to press: "Release without permission". It acknowledges that the older artifact has its advertising ID zeroed out on Android 13 and later,
which an ad-free build never reads. Do NOT press "Update declaration" and answer that the app does not use the advertising ID: 2.0.0 shows ads and
does use it, and a No there, with the permission in the manifest, is refused (and would be untrue).
When it goes away: when the old artifact is no longer active, that is, when a bundle with the permission has replaced it on every track that held it.
If you pressed "Release without permission" for an earlier upload, nothing needs undoing.


3. PERMISSIONS IN THE BUNDLE
============================
Asked for by the app: INTERNET, ACCESS_NETWORK_STATE. Added by libraries it uses (the Google Mobile Ads SDK, AndroidX work and the update library):
com.google.android.gms.permission.AD_ID, ACCESS_ADSERVICES_AD_ID, ACCESS_ADSERVICES_ATTRIBUTION, ACCESS_ADSERVICES_TOPICS, WAKE_LOCK,
FOREGROUND_SERVICE and the app's own DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION. Written into the manifest as removed: READ and WRITE_EXTERNAL_STORAGE,
SYSTEM_ALERT_WINDOW, VIBRATE, RECORD_AUDIO, CAMERA and REQUEST_INSTALL_PACKAGES (a store app may not install packages; the website's build
installs APKs through the browser, never through a permission), and three that libraries add for features the app does not use: USE_BIOMETRIC and
USE_FINGERPRINT (expo-secure-store's optional biometric prompt; the app keeps its session in the Android Keystore without one) and
com.google.android.finsky.permission.BIND_GET_INSTALL_REFERRER_SERVICE (Google Play's install referrer). check-bundle.mjs stops on any permission outside the list.
FOREGROUND_SERVICE is an ordinary permission and the app starts no foreground service; if the Console asks, say so.
The native app's seven ads permissions are all still there; the permission list is the same as 1.6.x to 1.7.1, so no new permission answer is due.

5. DATA SAFETY: ONE THING IS NEW
================================
Every answer of section 3 of PLAX-CONSOLE-ANSWERS-ADS.txt still holds: the ads library collects approximate location (IP address), app interactions,
diagnostics and device or other IDs, for advertising, analytics and fraud prevention, and shares them with Google; Plax collects name and email (with
Google sign-in), the account id, the picture address, topics and saved stories; nothing is sold; data is encrypted in transit; the account can be deleted
in the app and at https://plax-rouge.vercel.app/news/delete-account.

New in 2.0.0: when the app opens it asks Expo's update service (u.expo.dev) whether newer JavaScript is ready. The request carries the app's package version
and runtime version, the platform, the channel, the ids of the bundles it holds, and a random installation number made by the update library (EAS-Client-ID).
It carries no name, email, account, advertising ID or reading history (read from the library's own source, node_modules\expo-updates\...\FileDownloader.kt).
In the form this is an identifier ("Device or other IDs", which is already declared as collected) sent to a service provider that processes it for the app
(Expo), for "App functionality". Google does not count a transfer to a service provider that works on your behalf as "sharing", but the mapping is yours to decide
against the form's wording on the day. The privacy policy (updated 6 November 2026) and the app's About screen say so.

8. THE PUBLISHER'S NAME AND THE NEWS DECLARATION  (the owner's decision, with its risk)
=======================================================================================
What the code does: no card shows a publisher's name, in any build, the Google Play one too. The headline is the link to the story at its publisher (its
description for a screen reader gives the publisher's domain), and a story with no picture is headed by "Plax" on its poster. This is the owner's decision,
made on 6 November 2026 so that the app and the website match. The switch is features.sourceName in public\app-config.json (false now), with SHOW_SOURCE_NAME in
src\lib\app-features.ts for the website; a test keeps them equal. Setting both to true and pushing main brings the name back on the website and in the app, with no new bundle.
The native app's Google Play build behaved differently: it named the publisher whatever the file said, because of the policy below.
The risk: Google Play's News policy for aggregators says they "must provide users with clear information about the publishing sources of third-party content"
(support.google.com/googleplay/android-developer/answer/16189314). Plax is declared an aggregator, and the News declaration says each card shows the source name (1.5.5 file,
section 9). With no name on the card the app does not do what the declaration says, which Google may notice at review or later; Google has already sent Plax one News-policy
notice (16 October 2026, about contact details). Some publishers' feed terms also ask for a credit.
What to do, OWNER, one of:
  (a) accept the risk and leave the declaration as it is (what the code does today);
  (b) turn the names back on (two lines and a push) before or after the release; or
  (c) change the declaration to say that the source is shown on the story page (the link) and not on the card, and be sure Google accepts that.
Nothing was tried against Google's review: this is a description of a risk, not a finding.


9. UPDATING IN PLACE FROM THE NATIVE APP
========================================
Play updates an install of 1.x to 2.0.0 in place: same package, same app signing, higher version code. On the first start the app takes over, once, from the native
app's files: saved stories, the list of stories already seen, the language, the theme, the topics chosen for For you and the last feed. A signed-in reader signs in again (the native app sealed
the session with a key the new app cannot read); their topics and saved stories come back from their account. This was tried on the emulator, from a native 1.7.1 build (the website's
preview build, signed with the debug key) to the 2.0.0 preview build. It was not tried through Google Play itself.
The first start after the update is slower than later ones (the app starts its JavaScript and reads the old files); the emulator measured about 2 to 5 seconds to the first story.


10. OVER-THE-AIR UPDATES AND GOOGLE PLAY'S POLICY
=================================================
From 2.0.0 the JavaScript of the app can be updated without a new bundle (mobile\README.md, "Updates without a new bundle"). Google Play's "Device and Network Abuse" policy forbids an app to
download executable code (dex, JAR, native libraries) from anywhere but Google Play; it makes an exception for code run by an interpreter or virtual machine that gives only indirect access
to Android's APIs, and names JavaScript in a web view or browser as an example. The app's JavaScript runs in Hermes, an interpreter, and reaches Android only through React Native's modules; Expo's
documentation says EAS Update is for exactly this. That is Expo's and the owner's reading, not a ruling by Google. The native layer cannot be updated this way and never is: it comes only in a bundle.
What an update can change is limited by a check before it is published (native-fingerprint.js): a change to the native layer stops it.

12. SIZE: WHY THE FILE IS 55 MB AND A PHONE DOWNLOADS 14 MB
============================================================
Measured on 7 November 2026 with Google's bundletool on plax-2.0.0-play.aab (MB here is 1,048,576 bytes, as Windows shows it; in the thousands-based MB the file is 57.9 MB, the download 14.6 MB).
                                 the file   a 64-bit phone downloads   a 32-bit phone
  native 1.7.1 (code 18)          7.2 MB     3.2 MB                     3.2 MB
  React Native 2.0.0 (code 20)   55.2 MB    13.9 MB                    13.1 MB
The file holds what Play keeps for itself and what Play splits per phone: 18.7 MB of native debug symbols and 4.4 MB of R8's name mapping (the Console uses them to read crash reports; no phone receives
them), and the native libraries of four processor types, 22.9 MB, of which a phone gets the one it has (about 5.7 MB). Every phone gets the other 9 MB or so: the code (5.7 MB), the JavaScript (0.8 MB), the
resources (1 MB) and 1.2 MB of BouncyCastle files that nothing in Plax uses. The rise from 3.2 MB is React Native's own runtime (its core library, the Hermes engine, the image decoders it ships): the floor of a
React Native app, with code and resource shrinking already on. Google Play sends an update as the difference from the installed version. Nothing is changed for this: the file's size does not matter to Play.
What could be cut, and what it costs, is in mobile\README.md, "Publishing to Google Play", "Size"; the website's APK (77.4 MB, all four processor types, because an APK is not split per phone) is under
"Publishing the website's APK", "Its size".
